## 一、三类事实源

不要把“文档写了”“代码里有测试”“Runner 打印通过”混成同一件事。

| 事实 | 权威来源 | 回答的问题 |
|---|---|---|
| 产品覆盖 | Markdown 权威用例 | 应该测什么 |
| 执行声明 | 实际测试文件和 Runner 选择结果 | 本轮准备执行什么 |
| 运行证据 | 日志、截图、退出码、API 摘要 | 本轮真实发生了什么 |

测试函数数量、文件数量和历史报告不能代替逐 ID 覆盖追踪。一个测试函数可以覆盖多个用例，也可能一个用例都没完整覆盖。

## 二、从用例编译覆盖

以权威用例中的 ID 为主键逐条反查：

1. 找到实际测试文件中的同源元数据或声明。
2. 核对关键 Act 是否走 UI 前门。
3. 核对交互、展示、持久化三层断言。
4. 核对 actor、capability、资源生命周期和清理。
5. 核对最近一次执行证据。
6. 把状态与证据/缺口写回同一用例行。

再把每个用例拆成 Step 反查：

| TC | Step | Actor | UI action | 即时断言 | 展示断言 | 数据 oracle | 清理 | 代码位置 |
|---|---:|---|---|---|---|---|---|---|

每一行都落实才是完整步骤。覆盖状态由最弱 Step 决定；缺失中间动作、接收端动作或必要断言时，整条用例为部分覆盖，并在缺口中写具体 Step 编号。

推荐用例摘要：

| ID | 优先级 | Actor | 自动化状态 | 执行状态 | 证据或缺口 |
|---|---|---|---|---|---|
| CAL-001 | P0 | A | UI+API | passed | runId、报告链接 |
| CAL-002 | P1 | A+B | API-partial | not-run | 缺 B 端 UI Act |

不要另建需要人工双写的 coverage registry。若 Runner 需要机器可读元数据，让实际测试声明成为唯一执行元数据源，并由工具机械扫描。

## 三、状态定义

### 自动化状态

| 状态 | 含义 |
|---|---|
| `UI+API` | 关键 Act 走 UI，且三层断言完整 |
| `API-partial` | 仅数据准备/接口或部分 UI 覆盖 |
| `implemented-unverified` | 脚本存在但没有有效运行证据 |
| `MANUAL` | 当前只能人工验证，并写明原因 |
| `BLOCKED` | 项目内缺少必要入口、能力或权威裁决 |
| `EXTERNAL` | 被未接入的外部系统阻塞 |
| `not-implemented` | 尚无对应脚本 |

### 执行状态

| 状态 | 含义 |
|---|---|
| `passed` | 当前版本、当前环境有完整证据且所有 actor 退出成功 |
| `failed` | 真实执行失败，必须带失败阶段与定责 |
| `skipped` | 按明确条件跳过，并说明条件 |
| `not-run` | 本轮未执行，不能写成通过 |

自动化状态和执行状态必须分列。“脚本已实现”不等于“测试已通过”。

## 四、可行性复核

在生成脚本前逐条检查：

### UI 前门

- 真实用户入口是否存在？
- 关键业务动作是否真的通过 UI 完成？
- 是否错误地用 API 替代了被测 Act？
- 卡片类场景是否执行了加入、忽略、接受等按钮？
- 双端场景是否让每个 actor 分别执行自己的 UI 动作并验证中间状态？

### 定位能力

- Web 是否有 role/testid？
- Flutter 是否有稳定实体 Key/Semantics？
- 相同文本或 Key 是否因响应式布局重复？
- 目标是否 `hitTestable`、可滚动到、未被弹层遮挡？
- 点击后可观察状态是什么？
- Finder 失败属于未构建、不可见、不可点击，还是权限/状态下不渲染？

### 数据预言机

- 哪个 API 能独立读回结果？
- 参与者状态变化后，当前角色是否仍有读取权限？
- 展开型日程使用主 ID、实例键还是时间键？
- API 无法观测时，DB 白盒查询是否只读且足够窄？

### 资源与清理

- `ephemeral`：每轮创建、按精确 ID 删除、残留审计。
- `suite`：套件内共享、套件结束统一清理。
- `persistent`：只核验；若修改先注册恢复动作，不默认删除。
- teardown 是否在第一个业务 Act 前注册？
- 当前用例断言后是否通过真实 UI 删除 ephemeral 数据，并由 teardown 精确 ID 兜底？

### 角色、设备和外部能力

- actor 是谁，实际账号具有什么 role/capability？
- 是否需要不同设备上的独立 Flutter 进程？
- 外部依赖是 hard、soft 还是 optional？
- 缺失时应 fail、skip 还是降级？

### 时间与刷新

- 时间是否始终位于可操作的未来窗口？
- UI、Arrange、API 是否共用时钟基准？
- 列表更新依赖推送、轮询、重进页面、手动刷新还是导航？
- 时区断言是否区分 UTC、事件墙钟和设备展示？
- 时间是否在每个步骤临近 Act 时现算？跨天、跨周和长延迟事件是否使用专用窗口与条件等待？

### 生产约束与代码证据

- fixture 是否满足客户端/服务端参数校验、资源存在性、成员关系和用途？
- 是否读过当前客户端路由、状态层、Service/SDK 与服务端接口/事件链？
- 是否只是因为定位困难就误判功能未实现？
- 为可测性增加的 Key 是否保持布局、焦点、手势和业务语义不变？

任何一项不具备时，先把用例标记为 `BLOCKED/MANUAL/EXTERNAL` 并写清最小缺口，不生成看似可运行的空壳。

## 五、旧用例补齐

历史状态可能已经过时。补齐旧用例时：

1. 重新扫描当前 UI、API、测试钩子和 Runner。
2. 按当前代码复核旧的 `未实现/API-partial/BLOCKED`。
3. 保留用例 ID，除非权威需求明确改变语义。
4. 修改步骤时同步修改对应脚本和证据字段。
5. 删除不再有效的阻塞说明，记录新的 provenance。
6. 不因为历史报告“曾通过”而跳过当前可行性检查。
7. 对照步骤编号检查脚本是否跳步、合并步骤或只保留最终断言。
8. 检查 clean run、dirty rerun、模块串跑和响应式端差异是否改变路径。

编辑用例还需形成最小变更矩阵：

| 类型 | 必测变更 |
|---|---|
| 标量 | 旧值 → 新值 |
| 集合 | 增加、删除、删除最后一项 |
| 资源引用 | A → B |
| 身份 | 修改前后主资源 ID 不变 |

## 六、选择与执行证据

Runner 应支持项目需要的 `all/module/modules/file/case` 范围选择。每次执行前输出：

- 规范化后的选择条件；
- 命中的测试文件和用例 ID；
- actor/device/capability；
- 总数及按模块计数；
- 未登记或找不到的请求项。

选择结果为 0 必须非零退出，并打印 `No tests selected` 及条件。Runner 输出 `No tests ran` 应归为 selection/runner 失败，绝不能当作业务通过或业务失败。

多进程执行必须记录每个 actor 的退出码和聚合退出码。只有以下条件同时满足才能写 `passed`：

- 选择非空；
- 所有关键步骤已执行；
- 所有 actor 成功退出；
- 没有测试结束后的异步异常；
- cleanup/residual audit 通过。

静态分析、Widget 测试、局部事件日志和历史 runId 只能作为局部证据；如果晚于该 runId 又修改了脚本或产品代码，不得继续沿用 passed。

## 七、模块总览机械汇总

每个顶级模块的权威用例文件按子模块汇总：

| 域 | 用例数 | P0 | P1 | P2 | 主要运行层 | UI+API | 部分覆盖 | 未实现/非自动化 |
|---|---:|---:|---:|---:|---|---:|---:|---:|

规则：

- 用例数和优先级从权威用例行统计。
- `UI+API` 只计逐步骤完整覆盖。
- 部分覆盖包括脚本触达但缺步骤、缺 actor 或缺必要断言。
- 未实现/非自动化汇总 not-implemented、MANUAL、BLOCKED、EXTERNAL。
- 完整覆盖率与脚本触达率分开，均不是通过率。
- 文档可按顶级模块合并，Dart/TS 脚本仍按业务域拆分，由唯一 Runner 选择。

## 八、反模式

- 用 `testWidgets` 数量当覆盖率。
- 文档、registry、脚本维护三份手工映射。
- 根据文件名猜用例而不扫描真实声明。
- 只截图、不做结构化断言。
- 把 Arrange 的 API 成功当作业务 Act 已覆盖。
- 把 `API-partial` 批量改名成 `UI+API`，但没有补 UI 操作。
- 把“脚本可编译”写成“已通过”。
- 选择为 0 仍返回成功。
- 同一用例存在两个当前状态。
- 用脚本文件存在或 TC 日志出现证明步骤完整。
- 只检查最终对象，漏掉用例要求的中间状态、其它实例或接收端。
- 为了提高覆盖率把未落实 Step 的用例标成 UI+API。
