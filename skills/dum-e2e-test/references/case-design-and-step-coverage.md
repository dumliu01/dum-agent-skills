## 一、模块边界和功能清单

先从产品导航、领域文档和代码所有权确定顶级模块，再列子模块：

- 邮箱、日历、会话消息等是顶级模块，各维护一份权威用例文件。
- 多日历、会议室、提醒属于日历子模块，不拆成平行权威文档。
- 脚本可按子模块或业务域拆分，文档结构与脚本组织不要求一一对应。

设计前建立功能清单，来源至少包括：

1. 产品需求中的用户能力和验收口径；
2. 技术方案中的状态、接口、异步事件和边界；
3. 客户端页面、路由、Provider/Service、稳定定位和刷新链路；
4. 服务端接口、校验、状态机、定时任务和事件投递；
5. 现有用例、脚本、历史缺口和真实运行证据。

自动化目标是覆盖全部主流程和基础功能，不要求穷举所有异常组合。至少覆盖：

- 创建、查看、编辑、删除等基础生命周期；
- 用户可以到达的主导航和核心操作；
- 关键角色或双端协作闭环；
- 关键集合、资源引用和状态变更；
- 会造成数据丢失、权限越界或主流程不可用的基础异常。

低价值排列组合、纯视觉细节和难以稳定自动化的外部异常可标为 P2、MANUAL 或 EXTERNAL，但必须写明取舍，不能无声遗漏。

## 二、权威用例文件结构

每个顶级模块只有一份当前权威 Markdown，至少包含：

### 覆盖总览

| 字段 | 说明 |
|---|---|
| 域 | 子模块/业务域标识与名称 |
| 用例数 | 当前域权威用例数量 |
| P0/P1/P2 | 各优先级数量 |
| 主要运行层 | local、local/ZIM、local/服务端任务等 |
| UI+API | 逐步骤完整覆盖数量 |
| 部分覆盖 | 至少一个步骤或断言未落实的数量 |
| 未实现/非自动化 | not-implemented、MANUAL、BLOCKED、EXTERNAL 汇总 |

总计和覆盖率必须由用例行机械汇总，不能人工估算。完整覆盖率与脚本触达率分开；部分覆盖不能计入完整覆盖。

### 子模块用例表

至少包含：

```text
ID / 优先级 / 状态
provenance
操作步骤
①交互与②展示预期
③数据预期
真实覆盖
证据 / 缺口
```

模块特有信息可增加 actor、运行层、前置条件、资源、刷新语义、清理、冲突编号等字段，但不得删除上述字段。

## 三、步骤与预期一一对应

每个用例采用同一编号写步骤和预期：

```text
步骤 1 ↔ 预期 1
步骤 2 ↔ 预期 2
...
```

每一步至少包含：

```text
actor + 前置页面/对象 + 一个业务动作 + 动作输入
→ immediate interaction/display assertion
→ 必要的数据 oracle
```

规则：

- 不把“创建、分享、接受、检查”压成一个无法审计的大步骤。
- 一个步骤包含多个连续 UI 小动作时，写清关键控件和最终业务动作。
- 每个步骤都有同编号预期；没有可观察结果的步骤需说明它为后续状态准备了什么。
- 多端用例每一步显式写 A 或 B；不允许 A 通过 service 替 B 完成前门动作。
- 中间状态属于产品语义时必须断言，不能只检查最终状态。
- 检查集合影响时要说明“检查全部对象”及不变对象，不能抽查一条代替。

## 四、单端与多端示例

### 单端：编辑重复日程的单个实例

操作步骤：

1. A 打开某个重复日程实例，选择“编辑此日程”，把会议室 A 改为会议室 B 并保存。
2. A 逐一打开目标实例、其它实例以及母系列对应的展开实例，检查会议室。

预期结果：

1. 保存成功，目标实例详情展示会议室 B；API 中主系列 ID 不变，并产生正确的单实例变更。
2. 目标实例为会议室 B，其它实例仍为会议室 A；母系列规则不变。

### 多端：A 分享日程，B 加入后自动接受

操作步骤：

1. A 创建不包含 B 的日程，并从真实 UI 分享给 B。
2. A 检查参与人列表。
3. B 在分享通知中执行“加入日程”。
4. A 按产品刷新语义重新检查参与人列表和 B 的 RSVP。

预期结果：

1. B 收到对应 eventId 的分享通知。
2. B 尚未出现在日程参与人中。
3. B 加入成功，B 端进入或可打开目标日程。
4. B 出现在参与人中，状态为 accepted；组织者端和 API 状态一致。

## 五、逐步骤脚本覆盖审计

生成脚本前建立步骤映射：

| TC | Step | Actor | UI action | 即时断言 | 展示断言 | 数据 oracle | 清理 | 代码位置 |
|---|---:|---|---|---|---|---|---|---|

完整覆盖条件：

- 每个文档步骤都有真实脚本实现；
- 被测动作走 UI 前门；
- 每个关键中间状态和最终状态有有效断言；
- 数据变化有独立 API/DB 预言机；
- 多端各自执行属于自己的动作；
- 清理和恢复已登记。

以下不能证明步骤已覆盖：

- 只打印日志或 TC 名称；
- 只有注释、case declaration 或空 helper；
- 直接调用 Provider/Service/SDK 代替被测 UI 动作；
- 只断言最终一条记录，跳过中间步骤；
- 只验证 API 正确而没有 UI 展示；
- finder 存在但未证明可操作，也没有点击后状态变化。

覆盖状态由最弱步骤决定。任一步缺 UI action、必要断言或 actor 动作，整条用例只能标为部分覆盖，`evidence_or_gap` 必须指出具体步骤号。

## 六、从代码确认可实现性

不轻易判断“功能未实现”或“脚本无法编写”。下结论前依次检查：

1. 当前页面入口、响应式导航分支和权限条件；
2. Widget/DOM 是否懒构建、屏外、遮挡或需要展开子菜单；
3. 客户端路由、Provider/Service 和 SDK 事件桥接；
4. 服务端接口、参数校验、异步任务和状态字段；
5. 现有测试 Key/Semantics、Robot 和 API Gateway；
6. 历史脚本是否只是定位方式过时。

Finder 失败时区分四种状态：

```text
未构建 → 已构建但不可见 → 可见但不可点击 → 权限/状态下根本不渲染
```

只有确认产品入口或能力确实不存在，才能标记 BLOCKED/not-implemented，并附代码证据。

## 七、客户端代码改动账本

为可测性修改客户端前先列账本：

| 文件 | 改动类型 | 理由 | 功能/交互影响 | 权威依据 | 授权状态 |
|---|---|---|---|---|---|

改动类型：

- `test-metadata`：Key、Semantics、testid；可做最小改动，但要确认不改变布局、焦点和手势区域。
- `fixture-boundary`：测试环境入口或可观测接口；必须限制在测试环境。
- `business-logic`：导航、状态、缓存、事件桥接等真实业务行为；必须给出产品/技术依据并获得用户明确授权。

不能为了让脚本通过而偷偷改变业务逻辑，也不能用 Robot 绕过 E2E 稳定复现的真实视口或交互 Bug。

## 八、边界与状态组合

脚本设计至少检查与模块相关的以下状态：

- clean run 与 dirty rerun：首次创建和已有残留/已有配置路径是否不同；
- 单文件执行与模块串跑：前一用例是否泄漏页面、弹窗、账号、资源或 stage；
- 桌面分栏与移动端 push：返回、切 Tab 和重新进入路径是否不同；
- 普通日与跨天/跨周：周末、月末和跨午夜是否需要真实导航；
- 即时结果与长延迟事件：邮件、scanner、push 使用按业务 ID 的条件等待和独立超时；
- 发起端与接收端：事件型功能必须验证接收端 UI、缓存和持久化闭环；
- 第一次添加与非第一次添加：入口、空状态、重复资源和确认控件是否变化。

这些状态只在与模块语义相关时纳入，不机械生成无价值的笛卡尔积。
