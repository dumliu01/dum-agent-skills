# 合并代码技能

## 目标

把用户指定的代码安全整合进目标分支，避免三类事故：源/目标搞反、旧代码覆盖新行为、冲突文本干净但行为错误。

角色定义：**目标分支接收改动，源分支提供改动**。不能凭当前检出的分支或分支新旧来猜角色。

## 红线（任何时候不做）

- 源、目标、操作方式没确认前，不执行任何改 Git 状态的命令：merge / rebase / cherry-pick / reset / stash / 带改动的 checkout / commit / push / abort。
- 不用 `ours` / `theirs` 批量解决冲突，每个冲突单独按行为意图判断。
- 不主动 fetch / pull / 强推 / 自动提交 / 重写共享历史；远端有更新不等于要替换本地工作。
- 不丢用户的脏工作区和未提交改动；需要 stash、丢弃、处理进行中的 Git 操作或受保护分支时，停下问。
- 不用无关修改、整文件格式化、依赖升级、大范围重新生成来"解决"冲突。
- 提交和推送只在用户明确划入本次范围时执行，且先展示 diff 和验证结果。

## 流程

### 1. 预检：只读收集事实

```sh
git status --short --branch
git branch -vv
git log --graph --decorate --oneline --all -n 40
git merge-base <target> <source>
git merge-base --is-ancestor <source> <target>   # 源已在目标里？
git merge-base --is-ancestor <target> <source>   # 目标已在源里？
git rev-list --left-right --count <target>...<source>
git diff --stat <target>...<source>
```

说清：当前分支、目标、源、共同基线、双方各自独有的提交数、重叠文件、脏文件、是否有进行中的 merge/rebase、上游跟踪状态。

源分支过旧、已分叉、或可能撤销目标上的新行为时，不凭直觉合；先确认要保留的具体提交或行为。只挑部分提交、另开源分支，都只能作为待确认方案提出。

### 2. 说明计划并确认

固定句式：

> 将 `<source>` 的 `<N>` 个独有提交整合到 `<target>`；共同基线 `<base>`，目标侧独有 `<M>` 个提交。用 `<merge/rebase/cherry-pick>`，预计影响 `<文件/行为>`，不包含 `<非目标>`。

出现任一情况必须等用户确认再动：方向、操作方式或验收条件有歧义；源过旧或已分叉；分支受保护或会重写历史；工作区不干净或需要 stash / abort / reset；冲突涉及产品行为、生成文件、依赖或删除；用户要求先看计划。等待期间不编辑任何文件。

### 3. 执行

- 确认后重查 `git status` 和分支顶端，事实变了就停下重新确认。
- 记下操作前的分支名和 `HEAD` hash，便于恢复。
- 用用户选定的操作，不静默把 merge 换成 rebase / squash / cherry-pick。
- 普通 merge 必须切到目标分支上做。
- 出现冲突或意外文件立即停止自动流程，逐文件审查后才 `--continue`。

### 4. 按三方语义解冲突

对每个未合并路径：

1. `git diff --name-only --diff-filter=U` 列路径，`git ls-files -u` 看阶段；用 `git show :1:<path>`（基线）`:2:`（目标）`:3:`（源）对比三方和相关提交。
2. 按预期行为决定，不是选看起来更新的文本；两边行为兼容就合并，不确定不猜。
3. 删除、重命名、API / Schema、依赖与锁文件、生成文件、迁移、测试的冲突都要按语义确认；从需求、代码、测试、历史都判断不了的，保留未解决状态问用户。
4. 每解决一个路径只暂存该路径并看 diff，不批量 add / checkout；确认没有残留冲突标记和意外暂存。要改约定范围外的内容就停下确认。

### 5. 验证：只测本次责任范围

先界定**责任变更集**：用户要求合入的源提交或文件，加上本次实际做的冲突解决。目标分支原有提交、为追平远端顺带带入但没冲突的代码，都不在验证范围内。

必做：`git diff --check`；搜索跟踪文件里的 `<<<<<<<` `=======` `>>>>>>>`；对照约定的文件和行为检查最终 diff，特别是删除和重命名；确认 `HEAD` 在目标分支、提交图正确、操作前的本地改动没丢。

测试按下表触发：

| 情况 | 动作 |
|---|---|
| 无冲突自动合并（哪怕含代码） | 不跑测试，只做上面的 Git 完整性检查 |
| 只有文档 / 配置 / 锁文件 / 生成文件冲突 | 不跑测试，除非用户要求 |
| 实际解决了源代码冲突 | 不必再问，自动跑与冲突代码直接相关的**最小单元测试集**；不扩到未冲突模块或全仓 |
| 集成 / 接口 / E2E / UI / 冒烟 / 性能 / 全量回归等非单元测试 | 先说明命令、范围、预计成本和原因，问过再跑；合并或推送的授权不包含这些测试 |
| 测试命令混合了单元与其他类型 | 只跑能独立拆出的单元测试子集；拆不开就先问 |

补充规则：测试类型按目录、命名、项目脚本和仓库规范判断，不能因为命令是 `go test` 或 `flutter test` 就当成单元测试。构建、类型检查、lint 只在改动路径或项目规范要求时做。会改写锁文件、生成文件或下载依赖的验证，先确认确属必要，跑完检查工作区，不把副作用带进提交。

测试失败时区分三类：整合错误、语义冲突、原本就有或环境问题。不隐藏失败，不改无关代码；不确定就在提交前停下报告。

### 6. 停止与报告

整合完成、验证通过就停，不追加清理、重构、文档或远程操作。以下情况中止并询问：方向证明不了、旧代码可能撤销新行为、冲突语义不明、预检后分支变了、工作区保不住、出现无关失败。需要放弃进行中的操作时，说明状态，给出破坏性最小的恢复方式（通常是原生 abort），确认后再执行。

最终报告写清：源 → 目标、操作方式、操作前 `HEAD`、共同基线、提交数量、处理过的文件与冲突及行为依据、验证命令与结果、当前状态（已提交 / 已暂存 / 未完成 / 未推送）、需要用户决定的事。
