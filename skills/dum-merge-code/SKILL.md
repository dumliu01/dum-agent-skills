# 合并代码技能

## 目标

安全整合用户指定的代码，避免源/目标分支搞反、旧代码覆盖新行为，以及“文本干净但行为错误”的冲突结果。目标分支接收改动，源分支提供改动；不能仅凭当前检出分支或分支新旧判断角色。

## 安全门禁（强制）

1. 源分支、目标分支、操作方式和确认边界未明确前，不得执行改变 Git 状态的操作，包括 `merge`、`rebase`、`cherry-pick`、`reset`、带本地改动的 `checkout/switch`、`stash`、提交、推送和中止操作。
2. 不得把 `ours`/`theirs` 作为批量冲突策略；每个冲突都要按具体操作和行为意图判断。
3. 未经用户明确要求并确认影响，不得 `fetch`、`pull`、强制推送、自动提交或重写共享历史；不得因远程更新就替换本地工作。
4. 保留脏工作区和用户已有改动；遇到进行中的 Git 操作、钩子、受保护/共享分支或必须 stash/丢弃时停止询问。
5. 不得用无关修改、整文件格式化、依赖升级或大范围重新生成来解决冲突；生成/锁文件规则不明确时先询问。
6. 冲突解决后先展示 diff 和验证结果；提交、推送或其他远程操作只有在明确属于本次范围时才执行。

## 预检：先获取只读事实

改变引用、索引或工作区前，先识别方向错误、过旧源分支和本地未提交改动：

```sh
git status --short --branch
git branch --show-current
git branch -vv
git log --graph --decorate --oneline --all -n 40
git merge-base <target> <source>
git merge-base --is-ancestor <source> <target>
git merge-base --is-ancestor <target> <source>
git rev-list --left-right --count <target>...<source>
git diff --stat <target>...<source>
```

记录并说明当前检出分支、目标分支、共同基线、双方独有提交、祖先关系、重叠文件、脏/未跟踪文件、已有 sequencer/冲突状态、上游跟踪和远程新鲜度。

源分支过旧、已分叉，或可能撤销目标分支新行为时，不要凭直觉合并；先确认要保留的具体提交/行为。只挑选必要提交或创建新源分支只能作为待确认方案。

## 确定操作并确认

先说明计划：

> 将 `<source>` 的 `<N>` 个独有提交整合到 `<target>`；共同基线为 `<base>`，目标侧独有 `<M>` 个提交。计划使用 `<merge/rebase/cherry-pick>`，预计影响 `<files/behaviors>`，不包含 `<non-goals>`。

出现以下任一情况时，继续前必须明确确认：

- 源/目标方向、操作方式或验收条件缺失/有歧义。
- 源分支过旧/已分叉，分支受保护/共享，或操作会重写历史。
- 工作区不干净、已有 Git 操作进行中，或需要 stash/abort/reset。
- 冲突涉及产品行为、生成文件、依赖或删除决策。
- 用户要求试运行、先审计划或“先确认”。

确认须列出源 → 目标、操作、基线/提交数量、预期文件/行为、风险和最小替代方案；等待期间不得编辑。

## 执行最小且安全的整合

确认后重新检查 `git status` 和分支顶端；事实变化时停止并重新确认。

- 优先执行用户选择的操作。不得静默把 merge 改成 rebase、squash 或 cherry-pick。
- 记录操作前分支名和 `HEAD` hash 以便恢复；除非用户要求，不创建额外 tag/引用。
- 普通 merge 必须在目标分支执行，不能因当前检出源分支就在那里合并。
- rebase/cherry-pick 在每个可能冲突的步骤前核对提交顺序和目标；出现意外冲突立即停止。
- 报告冲突或意外文件时停止自动流程；逐文件审查前不得 `--continue`。

## 按三方语义解决冲突

对每个未合并路径：

1. 用 `git diff --name-only --diff-filter=U` 列出路径，用 `git ls-files -u` 查看阶段。
2. 对比共同基线、目标/ours、源/theirs（可用时 `git show :1:<path>`、`:2:<path>`、`:3:<path>`）及相关提交。
3. 按预期行为决策，而不是选择看起来更新的文本；兼容行为合并，不确定时不猜。
4. 删除、重命名、API/Schema、依赖/锁文件、生成文件、迁移和测试冲突都要按语义确认；无法从需求、代码、测试和历史确定时保留未解决并询问用户。
5. 每解决一个路径只暂存该路径并检查 diff；禁止批量 add/checkout。继续前确认没有冲突标记或意外暂存路径；若需改动约定范围外内容，停止并确认。

## 完成前验证

先界定“本次责任变更集”：用户要求合入的源提交/文件，以及本次实际产生的冲突解决。测试只由本次是否实际解决代码冲突触发；无冲突合并即使包含代码也不自动运行测试。目标分支原有提交、为追平远端而一并带入但未发生冲突的代码，不纳入测试范围。

按责任变更集检查：

- 执行 `git diff --check`，搜索跟踪文本文件中的 `<<<<<<<`、`=======`、`>>>>>>>`。
- 将 `git diff --cached`（或最终 merge diff）与约定文件/行为对照，检查删除和重命名。
- 无冲突合并不运行任何测试；只执行 Git 完整性检查以及变更类型对应的轻量检查。包含代码但自动合并成功，不构成运行单元测试的理由。
- 仅当本次实际解决了源代码冲突时，才可无需再次询问，自动运行与冲突代码直接相关的最小单元测试集合；不得扩展到未冲突模块或全仓测试。先按测试目录、命名、项目脚本和仓库规范判断测试类型，不能仅因命令是 `go test`、`flutter test` 或类似形式就认定为单元测试。
- 只有文档、配置、锁文件或生成文件发生冲突，而未解决源代码冲突时，不自动运行单元测试；用户明确要求时除外。
- 集成测试、组件测试、接口功能测试、端到端（E2E）测试、UI/设备测试、系统/冒烟测试、性能测试、需要真实服务或容器的测试，以及全量回归等非单元测试，执行前必须说明命令、范围、预计成本和原因，并询问用户是否运行；合并或推送授权不等于这些测试的授权。
- 如果一个测试命令混合包含单元测试和其他类型，优先选择可独立运行的单元测试子集；无法可靠拆分或辨别时，不自动执行，先询问用户。
- 只在改动路径、冲突语义、用户验收要求或项目规范明确要求时构建、类型检查或 lint；避免把针对性验证扩大为全仓构建或检查。
- 合并远端更新仅为完成提交/推送时，远端无冲突代码不构成本次测试理由；只有实际解决代码冲突才自动运行对应的最小单元测试，其他类型测试仍须先询问。
- 运行可能改写锁文件、生成文件或下载依赖的验证前，先确认它确属必要范围；验证后检查工作区，不得把测试副作用带入提交。
- 确认提交图、`HEAD` 位于目标分支，且操作前本地改动未丢失。

测试失败时区分整合错误、语义冲突和已有/环境问题；不隐藏失败或修改无关代码。不确定时在提交前停止并报告状态。

## 停止与中止

整合完成且验证通过后立即停止，不追加清理、重构、文档、发布说明或远程操作。无法证明方向、旧代码可能撤销新行为、冲突语义不明、分支在预检后变化、工作区无法保留或出现无关失败时，中止并询问，不要猜测。

必须放弃进行中的操作时，说明状态并提供破坏性最小的恢复方式（通常是原生 abort）；除非用户明确要求，否则确认后再执行。

## 最终报告

简要报告源 → 目标、操作、操作前 `HEAD`、共同基线、提交数量、已处理文件/冲突及关键行为依据；列出验证命令和结果，说明是否已提交/暂存/未完成、未推送的事实，以及需要用户决定的问题。
