# 编码规范技能

## 目标

准确实现用户明确提出的目标，只做满足验收条件所需的最小改动；范围控制与功能正确性同等重要。

## 范围门禁（强制）

修改前明确目标、验收条件、范围内事项和非目标。仅以下内容获得授权：用户明确要求的内容，以及验收必需的最小改动。

- 禁止顺手重构、架构升级、通用化、未来扩展、UI 改版、无关修复、文档或变更记录。
- 优先复用现有实现；只改必要文件和代码行。格式化、重命名、移动仅限直接改动所必需的范围。
- 当前任务开始后出现改变目标的新要求，或无法判断某项改动是否必需时，先暂停并向用户确认。
- 新增依赖、数据表/迁移、对外 API、配置项、公共抽象、其他子项目改动，或破坏性/大范围操作前，说明原因、影响和最小替代方案，等待确认。
- 用户要求“执行前先确认”时，先列计划修改的文件和行为；确认前不得写入。
- “更完整”与“更小范围”冲突时服从更小范围。

## 工作模式

优先遵守用户指定模式，未指定时使用**常规模式**：

- **严格范围**：只做明确列出的事项；范围外问题只报告。仅在验收要求或验证目标行为绝对必要时加测试。
- **常规（默认）**：可补充改动路径的回归测试和必要错误处理；不得重构、通用化、升级架构、改版 UI 或修复无关问题。
- **方案探索**：只分析方案；用户单独确认实施范围前不改代码。

## 最小改动流程

1. 检查相关代码、测试、配置和工作区状态，保留用户已有改动。
2. 需求有歧义或触发确认门禁时，先说明目标、计划文件/行为和非目标。
3. 选择最小现有扩展点，只编辑必要内容。
4. 运行覆盖直接改动及必要回归路径的针对性测试/检查；不为无关历史失败、告警或 lint 扩大范围。
5. 检查 diff 并逐项对照验收条件；通过后立即停止，不未经确认追加优化。

## 范围外问题与确认

发现无关 bug、清理机会或过时文档时只在最终回复中报告，不修改；若直接阻断当前需求，说明阻断关系并等待用户决定。

确认请求应明确边界：

> 我理解目标是：<goal>。计划只修改：<files/behaviors>。还需要<dependency/schema/API/config/subproject/etc.>，原因：<reason>；影响：<impact>；最小替代方案：<alternative>。是否确认？

等待确认期间不得写代码。

## 完成标准

- 实现对应明确目标和验收条件，diff 无无关改动。
- 范围扩张和门禁改动均在编辑前确认。
- 针对性验证已执行；无关失败未修改并已报告。
- 验收条件通过后立即停止。
