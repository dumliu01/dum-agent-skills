# 接口清单：抽取规则与优先级/模块分配

> 用途：指导 `dum-server-api-test` 技能阶段①「摄入与探测」，从需求/技术方案/代码三源按权威阶梯抽出每个接口的完整契约，并给出模块字母与优先级的分配规则。
> 本文件是**方法论 reference**，不含可运行实现代码。

---

## 1. 权威阶梯与来源

需求 > 技术方案 > 代码。抽取每个接口字段时按此阶梯依序查找：

1. **需求**（`docs/product-design/`、原始需求文档）——若明确描述了接口行为/边界，以此为准。
2. **技术方案**（`docs/tech-design/`）——接口契约（method+path、schema、错误码）的主要来源，通常比需求更结构化。
3. **代码**（handler/router/DTO/中间件）——需求与方案缺失或含糊时兜底；也用来核对方案是否与实现一致（不一致时按权威阶梯以更高层为准，并在清单中标注差异，提示可能需要 `dum-doc-reconcile`）。

每个接口字段抽取后，建议在内部记录来源层级（需求/方案/代码），供后续用例设计与失败定责时追溯。

---

## 2. 每个接口需要抽取的字段

| 字段 | 说明 |
|---|---|
| method + path | HTTP 方法 + 路径（含 path 参数占位） |
| 鉴权 | 鉴权方式（token/签名/session/无鉴权），以及鉴权失败的预期响应 |
| 请求体字段 | 逐字段列出：必填/可选、类型、约束（长度/范围/枚举/格式） |
| 响应体 + 错误码 | 成功响应结构；已知错误码列表及各自语义 |
| 前置依赖 | 调用该接口前需要先创建/准备的资源（如需先创建账号才能登录） |
| 副作用 | 是否产生资源、是否删除资源、是否扣费、是否触发通知/异步任务等不可逆或有代价的操作 |

## 3. 接口清单表模板

| 接口 | 模块字母 | 优先级 | 依赖 | 副作用 |
|---|---|---|---|---|
| `POST /agents/register`（RegisterAgent） | A | P0 | 无 | 产生 1 条 agent 记录（需清理） |
| `GET /agents/{id}`（GetAgent） | A | P1 | 需已存在 agent | 无 |
| `DELETE /agents/{id}`（DeleteAgent） | A | P1 | 需已存在 agent | 删除资源（不可逆） |
| `POST /instances`（CreateInstance） | B | P0 | 需已存在 agent | 产生 1 条实例记录（需清理） |

> 表中「接口」列建议同时记录 method+path 与接口的语义名（供 `@interface` 注解与 `run.sh --interface` 匹配使用）。

---

## 4. 优先级分层规则

| 优先级 | 定义 |
|---|---|
| **P0** | 核心正常流程 + 关键异常（鉴权失败、关键参数非法导致请求整体不可用） |
| **P1** | 常规异常（参数类/依赖类/幂等冲突类中非关键路径的场景） |
| **P2** | 边界/极端场景（超长输入、极端并发、罕见枚举组合等） |

分层时优先保证每个接口至少有 1 条 P0 用例（核心正常流程）；关键异常（如无 token 访问需鉴权接口）即使属于"异常"，也应标 P0，因为它验证的是接口最基本的安全边界。

具体异常场景的分类与断言要点见 `abnormal-catalog.md`。

---

## 5. 模块字母分配规则

- **一个功能域一个字母**：按业务功能域（而非单个接口）划分模块，用连续大写字母 `A/B/C…` 依序分配。
- **与参考项目保持一致**：若目标项目已有类似的模块划分惯例（例如已有测试工程用 A 表示注册管理），沿用其编号，避免同一项目内字母含义漂移。
- **示例**：

  | 字母 | 功能域 |
  |---|---|
  | A | 注册管理（Agent/账号的注册、查询、删除） |
  | B | 实例管理（实例创建、启停、查询） |
  | C | 消息/通知 |
  | … | 按需继续分配 |

- 模块字母与优先级共同构成测试文件与函数命名的骨架，具体拼装规则见 `naming-and-selection.md`。
