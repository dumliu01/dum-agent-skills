# dum-solution-design（个人技术方案设计规范）

## 概览

本 skill 是个人技术方案设计规范，强制使用 5 模块结构、文档/代码分离和文件命名约定。

**核心原则**：方案文档只讲**逻辑和决策**，不写示例代码。代码设计若必需，单独成文。

**可读性原则**：先讲业务问题、参与者和预期结果，再讲技术实现。业务词优先；必须使用的专业术语在首次出现时给出中文释义、作用和上下文，避免只堆英文缩写。

**绘图工具默认 = Mermaid**：架构图 / 模块图 / 时序图 / 流程图全部默认使用 Mermaid（直接在 markdown 里写 ```mermaid 代码块，无需额外 skill），不要默认走 PlantUML / `superpowers:uml`。仅当 Mermaid 真表达不了（如某些 PlantUML stdlib 特殊图形）时才回退 PlantUML。

## 何时使用

| 触发场景 | 例子 |
|---|---|
| 用户明确请求技术方案 | "出个技术方案" / "做个方案设计" / "设计一下 XX 模块" |
| 用户描述需求 + 提供参考材料 | 需求描述 + 截图 / 参考链接 / 类似产品举例 |
| 实现前规划阶段 | 用户说 "帮忙实现 XX 功能"，且复杂度足够需要先写方案而非直接编码 |
| 重要重构 / 跨模块改造 | 影响 ≥ 2 个模块、需要团队对齐设计 |

## 何时不使用

- 用户只要小修改（< 50 行代码 / 单文件变更）→ 直接改
- bug 修复 → 用 superpowers:systematic-debugging
- 已有 brainstorming spec → 用 superpowers:writing-plans 直接出 plan
- 一次性脚本 / 实验代码 → 不写方案

## 输出规范

### 文件位置（强制）

所有方案文档放到项目的 `docs/tech-design/` 目录（**不是**项目根的 `方案设计/`、也**不是** `docs/` 根 或 `docs/product/`）。如果项目没有这个目录，先创建。

少于 20 篇时平铺；达到阈值后按模块放入 `docs/tech-design/<模块>/`，零散方案放 `_misc/`，模块清单维护在 `README.md`。

### 按量自动分子目录（强制）

落盘新方案**前**，先数 `docs/tech-design/` 根目录下直接平铺的 `.md` 数（不含 README、不含子目录里的）：

| 状态 | 判定 | 动作 |
|---|---|---|
| 已分目录 | 根下已有非 README 子目录 | 读 `README.md` 模块清单：命中已有模块就放进 `<模块>/`；确属新模块才新建子目录 + 往清单补一行；都不沾放 `_misc/` |
| 未分 · 平铺 < 20 | 平铺数 < 20 | 直接平铺写入，不建子目录 |
| 未分 · 平铺 ≥ 20（首次触发） | 平铺数 ≥ 20 且无子目录 | ① 读现有方案标题/关键逻辑**语义聚类**出模块草案（模块名 + 文件→模块映射）→ ② **停下给用户确认/调整** → ③ `git mv` 建 `<模块>/` 搬文件、写 `README.md` 模块清单 → ④ 新方案写入对应子目录 |

**红线**：tech-design 首次分模块必须先出草案、等用户确认，**不可静默搬动存量文件**。

### 文件命名（强制）

| 文件类型 | 格式 | 示例 |
|---|---|---|
| 主方案文档 | `YYYYMMDD-方案名称.md` | `20260425-FundamentalAnalyst.md` |
| 代码实现文档（可选） | `YYYYMMDD-方案名称-代码实现.md` | `20260425-FundamentalAnalyst-代码实现.md` |

**强约束**：
- 日期用 `YYYYMMDD` 格式（无分隔符）
- "方案名称" 用驼峰或英文短语，避免空格 / 中文括号 / 路径敏感符号
- 代码实现文档**仅当需要**时创建，不强制
- 已分模块的项目，路径为 `docs/tech-design/<模块>/YYYYMMDD-方案名.md`，文件名规则不变

## 5 个必需模块（主方案文档结构）

主方案文档 `YYYYMMDD-方案名称.md` 必须按下面顺序包含**全部 5 个模块**：

### 1. 架构设计 / 模块设计

**包含**：
- **架构图**（涉及多服务 / 多进程时）：服务/进程之间关系
- **模块类图**（单进程内）：程序内各模块/类之间关系
- **每个模块的作用说明**：1–3 句概括职责 + 依赖

图默认用 **Mermaid** 并嵌入文档；仅当 Mermaid 无法表达时回退到 `superpowers:uml`（PlantUML）。

### 2. 关键流程时序图

**包含**：
- 涵盖**关键流程**的时序图（**优先时序图**，不够再用流程图）
- 每个流程的前置条件 + 后置条件 + 错误分支

**经验法则**：
- 至少 1 个核心 happy path；复杂方案可加 2–3 个异常/并发/跨服务流程。
- 默认用 Mermaid `sequenceDiagram`，调用栈深度 ≤ 5 层；表达不了时回退 PlantUML。

**节点层级一致性（强制）**：
- 一张时序图先选定一个抽象层级，所有参与者保持同一层级：跨服务流程用客户端/服务节点；单服务内部流程用类或模块节点。
- 不要在同一张图中混用服务、类、模块和函数节点。函数调用属于节点内部细节，放在节点说明或关键逻辑中，不单独作为参与者。
- 确需跨层展示时，保留顶层节点并在括号中标明子模块，例如 `服务A`、`服务B（订单模块）`；不要写成 `服务A`、`订单模块`，以免误读为同级节点。
- 节点命名应能看出类型和业务职责；图下注明本图的抽象层级，以及跨层节点的父子关系。

### 3. 关键逻辑

**包含**：
- **本方案最关键要解决的问题**（业务难点 / 技术难点）
- **每个问题的解决方案**（关键步骤 + 设计选择 + 必要的理由与取舍）

**写法**：
- 每个关键问题单独成节，标题必须是能让读者直接看懂难点的**问题句**，例如：`#### 如何解决两个模块的数据一致性问题？`。
- 标题下直接用通俗、有顺序的语言说明解决方案：先说总体思路，再按业务发生顺序或处理步骤展开，最后说明结果以及必要的取舍。
- 当问题的成因不直观，或不说成因就难以理解方案时，在解决方案前增加“**为什么会出现这个问题**”，简要说清触发场景和根因；成因显而易见时省略。
- 只有存在真实设计分歧时才列候选方案；此时说清推荐哪个、为什么，以及其他方案的业务影响或放弃代价。
- **不写代码**，只描述算法、数据结构和决策逻辑。

### 4. 接口说明

**包含（仅当方案涉及 API / 服务调用 / 模块边界 API 时）**：
- API 端点 / 函数签名 / 消息格式
- 每个接口的：路径 / method / 入参 schema / 出参 schema / 错误码 / 鉴权

用表格或 OpenAPI 风格描述，并对齐项目现有 API 风格；**不写实现**，只写契约。

**可省略条件**：方案纯内部模块、无对外接口、无跨服务调用 → 此章节标记 "本方案无对外接口" 即可

### 5. 遗留问题

**包含**：
- 方案实现后**已知未解决**的问题
- 后续可优化方向（不属于本方案 scope 但相关）
- 重开触发条件（什么时候应该回来处理）

**写法**：
- 编号列表 P1 / P2 / P3...（重要性递减）
- 每个问题：现状描述 + 为什么本次不做 + 建议的处理时机

## 可读性与术语规则（强制）

### 业务词优先

- 每个章节先回答“谁在什么场景下做什么、成功后得到什么、失败会怎样”，再补充技术实现。
- 模块、流程和图的节点使用业务动作/对象命名；技术组件名放括号中。能用常见业务词时，不使用内部简称、框架名或英文缩写。

### 专业术语解释

- 术语首次出现使用“中文名称（英文/缩写）+ 一句话定义 + 本方案中的作用”，后续可直接使用简称。
- 例如不要只写 `Outbox`；写成“待发送事件记录（Outbox）：先把待发送消息写入业务库，再由后台任务投递，避免业务已成功但消息丢失”。如果方案不需要强调实现机制，直接写“消息待发送记录”即可。
- 缩写首次出现写出中文含义；代码类型名、表名、配置名可保留原文，但必须紧邻业务解释。
- 术语较多或面向非本领域读者时，在 5 个必需模块之后增加“术语说明”表：术语、通俗解释、本方案中的用途。术语少且已在正文解释时不重复建表。

### 阅读检查

- 图和箭头要能读出业务顺序，图下补 1–2 句结论；候选方案写清业务影响、选择理由和放弃代价。
- 接口、队列、缓存、事件、事务等词要说明解决的业务问题。交付前删掉不影响决策的术语/细节，对难懂词改用业务词或补解释。

## 文档与代码分离规则（强制）

### 主方案文档不写示例代码

**禁止内容**：
- ❌ 函数/类的代码实现（`def`/`class`/`function`）
- ❌ 完整 SQL 建表语句（除非是 schema 设计的一部分）
- ❌ 配置文件示例（除非是接口契约的一部分）
- ❌ 单元测试代码

**允许内容**：
- ✅ 函数签名 / 接口定义（描述契约，非实现）
- ✅ 数据 schema（字段名 + 类型 + 约束）
- ✅ 伪代码（仅当算法逻辑必须用代码表达 ）
- ✅ 命令行 / shell 命令示例（接口说明用）

### 何时创建 -代码实现 文档

**创建条件**（任一即可）：
- 方案涉及非平凡算法，需要给开发者代码参考
- 关键代码骨架必须显式展示（如复杂状态机 / DSL 设计）
- 实现包含技术 trick 容易写错（如并发原语 / lock-free 算法）

**不创建条件**：
- 标准 CRUD / boilerplate
- 跟现有代码模式一致的常规实现
- 测试代码

## 工作流

```
1. 触发后确认范围和关键决策。
2. 输出按顺序包含 5 个模块的主方案文档（图默认 Mermaid）。
3. 按条件决定是否另写 `-代码实现.md`。
4. 保存到 `docs/tech-design/`，交用户审核并按反馈修改。
5. 审核通过后再用 `superpowers:writing-plans` 进入实施规划。
```

## 快速参考

| 项 | 规则 |
|---|---|
| 输出位置 | `docs/tech-design/`；平铺 ≥ 20 篇按模块分 `docs/tech-design/<模块>/`（首次分模块需出草案+用户确认） |
| 命名 | 主文档 `YYYYMMDD-方案名称.md`；代码文档 `YYYYMMDD-方案名称-代码实现.md`（可选） |
| 结构 | 按顺序包含架构、时序、关键逻辑、接口、遗留 5 个模块；关键逻辑用问题句作小节标题；接口无关时写“本方案无对外接口” |
| 图与代码 | 图默认 Mermaid，必要时 PlantUML；主文档不写实现代码，复杂代码另写 `-代码实现.md` |
| 可读性 | 业务词优先；术语首次解释；时序图节点保持同一抽象层级 |

## 常见错误

| 错误 | 后果 | 修正 |
|---|---|---|
| 路径/命名不符 | 下游找不到或目录混乱 | 严格使用 `docs/tech-design/` 和 `YYYYMMDD-方案名称.md` |
| 主文档夹杂实现代码 | 方案与代码耦合、易过时 | 只写契约/伪代码，复杂实现另写 `-代码实现.md` |
| 缺架构图、时序图或遗留模块 | 关系、顺序或未决事项不清 | 补齐 5 模块；时序图优先于流程图 |
| 时序图混用服务、类、模块、函数节点 | 调用关系和上下级关系难以理解 | 一图一层级；跨层时写成“服务B（子模块）”，并在图下说明 |
| 关键逻辑用“问题 1”“数据一致性”等标签式标题 | 读者看不出具体要解决什么 | 改成“如何……？”类问题句，在下方按顺序讲清方案，必要时先解释成因 |
| 接口说明写成实现细节 | 契约与实现耦合 | 只写 path / method / schema / 错误码等契约 |
| 只堆英文术语或缩写 | 业务读者无法判断含义和影响 | 首次出现给中文释义、作用和上下文，能换业务词就替换 |
| 跨过 20 篇阈值或新建同义模块 | 文件分散、存量搬迁有风险 | 先读模块清单；首次分模块先出草案并等确认 |

## 红线 — 立即停止

出现以下任一情况就停下修正：主文档写入实现代码、路径/命名不符、缺少 5 个模块或核心时序图、关键逻辑的小节标题不是具体问题句、专业术语无解释、时序图混用抽象层级、用 ASCII 图替代 Mermaid，或首次分模块未确认就搬动存量文件。

## 相关技能

- **绘图**：默认 Mermaid；无法表达时再用 `superpowers:uml`。
- **实施规划**：方案审核通过后用 `superpowers:writing-plans`。
- **需求不清**：先用 `superpowers:brainstorming` 明确想法，再回到本 skill。
