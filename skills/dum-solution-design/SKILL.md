# dum-solution-design（技术方案设计）

## 目标

写一份**让读者看懂核心要点、能据此拍板和实施**的方案文档。章节为要点服务：基础骨架保证不漏关键面向，不同类型的方案再按需追加章节；不为凑结构写空话。

三条硬原则：

- **只讲逻辑和决策，不贴实现代码**。类名、对象名、接口名、方法签名、字段名可以写，用来描述模块关系和代码骨架；函数体、具体实现不写，必需的代码参考另写 `-代码实现.md`。
- **业务词优先**。先说谁在什么场景做什么、成功得到什么、失败怎样，再讲技术；术语首次出现给中文释义。
- **图默认 Mermaid**。直接写 ```mermaid 代码块；Mermaid 表达不了才回退 PlantUML（`superpowers:uml`），不用 ASCII 图。

## 何时使用 / 不使用

- 用：出技术方案、设计复杂功能或跨模块改造、基础架构/技术选型、根因已定位但改动影响面需要对齐的 bug 修复方案。
- 不用：小改动（单文件、几十行）直接改；bug 根因还没找到先走 `superpowers:systematic-debugging`；一次性脚本不写方案。

## 输出位置与命名（强制）

- 目录：`docs/tech-design/`（不是项目根 `方案设计/`，也不是 `docs/` 根）。没有就先建。
- 主文档 `YYYYMMDD-方案名称.md`；代码参考 `YYYYMMDD-方案名称-代码实现.md`（仅需要时）。方案名称用驼峰或英文短语，不含空格、中文括号。
- 按量分子目录：落盘前先数根目录平铺的 `.md` 数（不含 README、不含子目录内）。

| 状态 | 动作 |
|---|---|
| 已有子目录 | 读 `README.md` 模块清单：命中放 `<模块>/`；确属新模块才建目录并补清单；都不沾放 `_misc/` |
| 平铺 < 20 | 直接平铺 |
| 平铺 ≥ 20 且无子目录（首次） | 按标题/关键逻辑语义聚类出模块草案 → **停下等用户确认** → `git mv` 搬迁并写 `README.md` 清单 → 新方案入对应子目录 |

红线：首次分模块不可静默搬动存量文件。

## 文档结构：基础骨架 + 按类型追加

### 基础骨架（默认顺序）

| 段 | 讲什么 | 写法要求 |
|---|---|---|
| 0 概要 | 一句话方案、解决什么问题、影响范围（改哪些模块/服务/数据）、最关键的 1–2 个决策 | 5 行以内，放文档最前，让评审人一分钟决定要不要往下读 |
| 1 架构 / 模块设计 | 多服务画架构图，单进程画模块类图；每个模块 1–3 句职责 + 依赖 | Mermaid 嵌入文档；类图和模块说明可标出类名、关键方法签名、核心字段、调用/依赖关系，作为代码骨架参考，但不写方法体 |
| 2 关键流程时序图 | 至少 1 个主流程；复杂方案加异常 / 并发 / 跨服务流程；每图写前置条件、后置条件、错误分支 | 优先时序图；一图一抽象层级（见下） |
| 3 关键逻辑 | 本方案要解决的业务/技术难点及解法 | 每个难点单独成节，标题是问题句「如何……？」；先总体思路，再按发生顺序展开，最后说结果与取舍；成因不直观时先补「为什么会出现」；有真实分歧才列候选方案，说清推荐理由和放弃代价 |
| 4 接口说明 | 对外或跨模块契约：路径 / method / 入参 / 出参 / 错误码 / 鉴权 | 只写契约，对齐项目现有 API 风格；无接口写「本方案无对外接口」 |
| 5 待决策 | 需要用户拍板的开放问题：有分歧的选型、没确认的范围、缺的信息 | 每条写问题 + 候选 + 推荐及理由；**审核通过前必须清空**，拍板结果回填到对应章节；没有就写「无待决策」 |
| 6 遗留问题 | 明确本次不做、但已知的未解决问题与后续优化方向 | P1 / P2… 按重要性编号；每条写现状 + 为何本次不做 + 处理时机或重开触发条件；不要把该拍板的问题塞进来 |

骨架段可以合并，或标注「不适用」并写明原因，但**不能静默删除**。任何方案都不能省的是：概要、关键逻辑、待决策、遗留问题。

时序图层级规则：一张图的参与者保持同一抽象层级，跨服务流程用服务节点，单服务内部用模块或类节点；函数调用是节点内部细节，不做参与者；确需跨层时写成 `服务B（订单模块）`，不与 `服务A` 并列成同级；图下注明本图层级，并补 1–2 句结论。

### 按方案类型追加章节

先判断方案属于哪一类，把该类读者拍板和实施最需要的要点补成章节，放在骨架前后合适的位置：

| 类型 | 通常追加 |
|---|---|
| 新功能 | 需求与范围（做什么 / 不做什么）、数据模型变更、兼容与灰度策略 |
| 基础架构 / 技术选型 | 现状与痛点、选型对比（候选 / 评估维度 / 结论）、非功能指标（性能 / 容量 / 可用性 / 成本）、演进路线与迁移步骤、风险与应对 |
| bug 修复方案 | 问题现象与影响范围、根因分析（触发条件 + 出错机制）、修复方案与备选、验证方法（复现步骤 / 回归点）、是否需要修复存量数据 |
| 重构 / 迁移 | 现状问题、目标结构、分步迁移与回滚、兼容期策略（双写 / 双读 / 开关）、验收标准 |
| 性能优化 | 基线指标与瓶颈定位、优化手段与预期收益、压测验证方案、副作用与风险 |

不在表里的类型，自问「读者拍板或实施还缺什么」，缺什么补什么。追加章节同样遵守不贴代码、业务词优先。

## 文档与代码分离

- 主文档禁止：函数 / 类实现、完整建表 SQL（schema 设计本身除外）、配置文件示例、测试代码。
- 主文档允许：类名 / 对象名 / 接口名 / 方法签名 / 字段名（描述结构和依赖关系，作代码骨架参考）、数据 schema（字段 + 类型 + 约束）、必要的伪代码、命令行示例。
- 另写 `-代码实现.md` 的条件（任一）：非平凡算法需要代码参考；必须展示代码骨架（复杂状态机、DSL）；容易写错的技术细节（并发原语、lock-free）。标准 CRUD、与现有模式一致的常规实现、测试代码不写。

## 可读性

- 每章先回答「谁在什么场景做什么、成功得到什么、失败会怎样」，再讲实现。
- 模块、流程、图的节点用业务动作或对象命名，技术组件名放括号；能用业务词就不用内部简称、框架名、英文缩写。
- 术语首次出现写成「中文名（英文）+ 一句定义 + 在本方案中的作用」。例如不要只写 `Outbox`，写「待发送事件记录（Outbox）：先把消息写入业务库，再由后台任务投递，避免业务成功但消息丢失」。术语多或读者非本领域时，文末加「术语说明」表。
- 图和箭头要能读出业务顺序；接口、队列、缓存、事件、事务都要说明解决了什么业务问题。
- 交付前删掉不影响决策的细节。

## 工作流

1. 确认范围、方案类型和关键决策；想法不清先用 `superpowers:brainstorming`。
2. 按基础骨架写主文档，按类型追加章节；图用 Mermaid。
3. 按条件决定是否另写 `-代码实现.md`。
4. 按位置与分目录规则落到 `docs/tech-design/`，交用户审核；先让用户清掉「待决策」，把结论回填后再按其余反馈修改。
5. 审核通过后用 `superpowers:writing-plans` 进入实施规划。

## 自检（出现任一项即停下修正）

- 主文档出现实现代码（方法体、完整函数/类实现；只列类名和签名不算）；路径或命名不符；首次分模块未经确认就搬文件。
- 缺概要、关键逻辑、待决策或遗留问题；骨架段被静默删除而非标注不适用；待决策未清空就宣布审核通过；把该拍板的问题写进遗留问题。
- 关键逻辑小节标题不是问题句；术语无解释；时序图混用层级；用 ASCII 图代替 Mermaid。
- 该类型方案的核心要点缺失：bug 方案没根因和验证方法，架构方案没选型对比和非功能指标，迁移方案没回滚。

## 相关技能

- 上游：`superpowers:brainstorming`（需求不清时先明确想法）。
- 绘图回退：`superpowers:uml`。
- 下游：`superpowers:writing-plans`（审核通过后出实施计划）。
- 落点 `docs/tech-design/` 由 `dum-knowledge-base-build` 搭建，后续由 `dum-doc-reconcile` 对账。
