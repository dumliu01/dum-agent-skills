# dum-solution-design

> 出技术方案，目标是**把核心要点讲清楚**：基础骨架（概要 / 架构 / 时序 / 关键逻辑 / 接口 / 待决策 / 遗留）+ **按方案类型追加章节** + **文档与代码分离** + 命名/位置约定。

## 它做什么

方案文档常见三类病：（1）代码塞进设计里，重构后文档变垃圾；（2）少了"被否决方案"和"遗留问题"，下次重走弯路；（3）没有时序图，调用顺序看不出来。本技能用基础骨架保证不漏关键面向，再按方案类型补齐该类读者最关心的要点，并**禁止主文档贴实现代码**（类名、接口名、方法签名这类结构性命名可以写）——必要时另写一份 `-代码实现.md`。

**基础骨架**（默认顺序，可合并或标注不适用，不可静默删；概要、关键逻辑、待决策、遗留问题必须有）：
0. **概要** — 5 行内：一句话方案、解决什么问题、影响范围、关键决策
1. **架构 / 模块设计** — Mermaid 架构图或模块类图 + 各模块职责；可写类名、方法签名、字段名作代码骨架参考，不写实现
2. **关键流程时序图** — Mermaid sequenceDiagram，一图一抽象层级
3. **关键逻辑** — 以问题句作标题，按顺序讲清解法，必要时先说成因
4. **接口说明** — 只写契约（path / method / schema / 错误码）
5. **待决策** — 需要用户拍板的开放问题，审核通过前必须清空
6. **遗留问题** — 明确本次不做的事，P1/P2/P3 编号 + 重开触发条件

**按类型追加**：新功能补需求范围与灰度；基础架构补现状痛点、选型对比、非功能指标、演进路线；bug 修复补现象影响、根因、验证方法；重构迁移补分步迁移与回滚；性能优化补基线指标与压测验证。

## 何时触发

- ✅ "出个技术方案" / "方案设计" / "设计一下 XX 模块"
- ✅ 需求描述 + 参考截图 / 链接 / 类似产品
- ✅ "帮忙实现 XX 功能" 且复杂度需要先写方案
- ✅ 基础架构 / 技术选型设计，或跨 ≥2 模块的重构
- ✅ 根因已定位、改动影响面需要对齐的 bug 修复方案
- ❌ 小修改（<50 行/单文件）→ 直接改
- ❌ bug 根因未定位 → 先用 `superpowers:systematic-debugging`
- ❌ 已有 brainstorming spec → 直接走 `superpowers:writing-plans`

## 它交付什么

| | |
|---|---|
| 输出位置 | `docs/tech-design/`（**不是**项目根 `方案设计/`、也不是 `docs/` 根）；平铺 ≥ 20 篇后按模块分子目录，首次分模块需用户确认 |
| 主文档 | `docs/tech-design/YYYYMMDD-方案名称.md` |
| 代码实现（可选） | `docs/tech-design/YYYYMMDD-方案名称-代码实现.md`，仅当包含非平凡算法或难写对的骨架时 |
| 绘图工具 | **默认 Mermaid**（直接写 ```mermaid 代码块）；不够用再回退 `superpowers:uml` |

## 跟其它技能怎么衔接

- 上游可衔接 `superpowers:brainstorming`（想法未明时先 brainstorm）
- 下游接 `superpowers:writing-plans`（方案审核通过后落成可执行 plan）
- 方案产出落进 [`dum-knowledge-base-build`](../dum-knowledge-base-build/) 搭的 `docs/tech-design/`，下游 `dum-doc-reconcile` 据此对账

## 完整工作流

骨架各段写法、按类型追加章节表、文档/代码分离清单、自检项，详见 [`SKILL.md`](SKILL.md)。
